- **只读**：整个过程不写仓库、不写 VFS（文档最后才按业主指令落盘）；跑任何脚本前先 grep 它会不会写 VFS（`cdp-devview` 会往 Monaco 打字并通过 `/>` 写 `/sop_probe.md` ⇒ 因此**没跑**）。

## 2 真正改变过结论的发现（9 条，都带证据）
1. **`ui` 从不进逐节点件**：NodeView 构造的 props（:161）没有 `ui`；`ui` 只出现在 App 层（DevView.jsx:41）。〔码〕⇒ 契约里 `ui` 是“入口层独有字段”。
2. **root 从不进派发**：`DocPane` 直接 `ui.doc.kids.map(NodeView)`（:12-19），全 `lib/mods` 里读 `ui.doc` 的生产代码只有这一处。〔码〕⇒ “整树归一个件”必须**新开渲染入口**，不是“认领 root”。
3. **`NodeView` 未被导出**：`ui_core/package.json` 的 `exports`/`esmx.exports` 都没有 `./NodeView`（`esmx.exports` 也没有通配）。〔码〕⇒ 入口层拿不到 root 级 `renderNode`，这是 P4 形态选择的硬约束。
4. **F1 是唯一与 `?app=` 耦合的判据**：`cdp-devview` 的 H3/H4/H5 只断言 `timeOrigin` 与挂载，不读 `?app=`。〔码〕⇒ 形态解耦的判据代价可以精确到“一条断言的表述”。
5. **demo/test 里 10/11 个套件默认连 9222**（业主的 Chrome）；`exp_scripts` 多数默认 9223，但 `check.mjs` 默认 9222。〔码〕⇒ 这是系统性陷阱，不是手滑。
6. **`check-edit-dom` 根本没有 `process.exit`**（grep 0 命中）⇒ 它无论几红都退出 0，模块层必然记绿。〔码〕⇒ “MODULES 16/16”这个数字不能当不回归依据。
7. **剧本 app 早已存在**：`DOC`＋`SCRIPT` 在 `/render/实现.md`（都有 default），而 `check.mjs` 期望 `.sd-*` 上屏且 `D.std === 0`（“没有节点掉回 std”）。坏在两处：① 声明路径写成不存在的 `/实现.md`；② 它只是 node 级 trait、不是整块地的 owner。〔测+码〕⇒ 本方案因此从“从零写 app”变成“救活已有件 + 给它整块地”。
8. **J3 绑定了 α 实现方式**：我原写“任何页内跳转都不改壳段（`?wt&app` 原样）”；这在 β 下不成立（`?app=` 本身就是“当前篇”指针）⇒ 改成 **J3′**：换页/换篇不改 `?wt`、不改形态，`?app=` 的**值**可变。〔推〕
9. **`appRouter.subscribe` 双触发**：它同时挂 `hashchange` 与 `popstate`（:54-55）⇒ 对 hash 的历史导航会调两次；且 hash 视图的 `push` 只写 `location.hash`、不调 `notify`（:44）。〔码〕⇒ 订阅处理器必须幂等，且壳要能区分来源（否则后退一次就被壳改写历史）。

## 3 结构性结论（可复用的判断）
- **投递优先级**：挂在店上 / 走 props ＞ 模块级单例。依据：发布袋在“md 内嵌件 vs 宿主”之间是两个实例（note §67.3），而“通配导出不进 import map”（note §33.3）。
- **`appRouter` 是唯一例子**：源头可以是无状态单例，但**投递必须走 props**，且与节点件共用同一实例。
- **“同名多处”登记表**（改一处会漏的地方）：`provides` 4 处（entry.client 5 项 / entry.server 5 项 / entry.node 注释 / package.json 8 项）· 身份键 4 份（框架 nodeKey + std + region + card）· `spec` 两套解析（`uiMd.splitAddr` 与 `locator.parseSpec`）· URL 写点 4 处（switchWt / toggleDevMode / DevView fallback / appRouter）· “产品面”概念 4 处表达。
- **这套代码的主要风险不是“坏”，而是“同一件事有多个落点”**：13 条技术债里只有 3 条是产品缺陷，其余 10 条都是多处落点。
- **判据纪律**：口径必须分“复核 / 未复核”；数字带命令与退出码；**新增判据必须做“关掉功能看它是否变红”**（防恒真）；判据一律隔离串行（并发会互抢宿主）。
- **先立判据再加功能**：把今天已绿的源规则放在改动之前，让它们守住后续每一步（例：URL 写点白名单正好守住“别顺手写整条 URL”）。
- **“一段两义”的解法**：瞬态重叠 + 稳态归一（app 在页内段表达篇名 → 壳消费 → 壳把篇名搬进 `?app=`，页内段只留“页”）。
- **入口级两条硬约束**：入口件要自己 `observer`（DevView 只给 `memo`）；构件身份要稳（与 `memoOf` 同款纪律，否则每次渲染重挂）。

## 4 我自己纠正过的判断（10 处，留档）
1. 「唯一 URL 写点」→ **假**：两处壳级写点 + 一个能力。
2. 「`?app=` 只在开机读一次」→ 精修：模块初始化读一次，**效果**（自动开那篇）由 `autoOpened` 只跑一次。
3. 「`content` 的正确形态是 `renderNode`」→ “正确”是越权措辞，降为 P4 三案之一。
4. 「P4 由 P9 决定」→ 改成**互锁**（形态 1 ⇒ P9 只能不搬；P9 搬 ⇒ 必须形态 2/3）。
5. 「剧本 app 是重写型 α」→ 实为**薄壳 β**（把 PAPER 的形态误投影过来了）。
6. 「修声明坏点零影响」→ **零代码风险但不零渲染影响**：它会激活三条从未生效的 trait 规则。
7. 「S1.4 只是三行改动」→ 依赖 P11 取案；取“保持现状”则零改动。
8. 「用 MINA 当验收件」→ 不成立（它是节点件，形态 1 下拿不到 `node`）。
9. 「DOC 可能不可画」→ 实测有 default，可画（SCREEN 是 CSS 件，本就该被过滤）。
10. **词汇漂移**：槽位件 → “appview 的值”；DocBody → “文档体（提案代号，待命名）”；包 A/B/C → “最小/目标/折中包”；阶段 P0–P3 → “阶段 0–3”（与待拍板 P1–P16 撞名）。
